# اعلان ورود و زیرساخت ایمیل

## راه‌اندازی روی سرور

ابتدا نسخهٔ جدید را مستقر کنید و migration را اجرا کنید. هر دو کانال برای تمام نقش‌های موجود و نقش‌های جدید به‌صورت پیش‌فرض خاموش هستند.

```bash
php artisan migrate --force
php artisan config:cache
```

تنظیمات ایمیل را در `.env` سرور نگه دارید. برای سروری که تست sendmail و Tinker روی آن موفق بوده است:

```dotenv
MAIL_MAILER=sendmail
MAIL_SENDMAIL_PATH="/usr/sbin/sendmail -bs -i"
MAIL_FROM_ADDRESS=no-reply@Cardiware.ir
MAIL_FROM_NAME="Cardiware"
QUEUE_CONNECTION=redis
```

صف‌های ایمیل و پیامک از اتصال و صف پیش‌فرض برنامه استفاده می‌کنند؛ بنابراین پردازشگر فعلی `supervisor-1` در Horizon آن‌ها را پردازش می‌کند. پس از استقرار، اگر Horizon زیر نظر Supervisor اجرا می‌شود:

```bash
php artisan horizon:terminate
```

Supervisor باید Horizon را دوباره اجرا کند. اگر به‌جای Horizon از `queue:work` استفاده می‌کنید، `php artisan queue:restart` را اجرا کنید. برای اجرای دستی worker:

```bash
php artisan queue:work --tries=3 --timeout=60
```

در محیط عملیاتی از اتصال واقعی صف مانند Redis یا database استفاده کنید. اتصال `sync` پیام را در همان درخواست ارسال می‌کند. تنظیمات محلی به‌صورت `MAIL_MAILER=log` باقی مانده‌اند؛ برای ارسال واقعی، مقدار `.env` سرور باید `sendmail` یا transport واقعی دیگری باشد.

## تنظیم پنل مدیریت

۱. از «نقش‌ها»، گزینهٔ «اعلان ورود» نقش دلخواه را باز کنید.
۲. ایمیل، پیامک یا هر دو را فعال کنید. این تنظیم برای نقش پیش‌فرض و سوپرادمین هم در دسترس است و دسترسی‌ها یا عنوان آن‌ها را تغییر نمی‌دهد.
۳. برای پیامک، در «تنظیمات عمومی ← پنل پیامکی»، سرویس پیش‌فرض و اعتبارنامه‌های فعلی آن را تنظیم کنید و الگوی جداگانهٔ اعلان ورود را در پنل ارائه‌دهنده بسازید.
۴. شناسهٔ الگو و نام متغیرهای اعلان ورود را در همان صفحه وارد کنید.

الگو چهار مقدار دارد:

| مقدار | نام پیش‌فرض در SMS.ir و فراز | ترتیب در ملی پیامک |
| --- | --- | --- |
| نام نمایشی کاربر | `Name` | ۱ |
| زمان شمسی با ساعت تهران | `Time` | ۲ |
| IP ورود | `Ip` | ۳ |
| محل ورود: وب‌سایت یا لانچر | `Source` | ۴ |

نام متغیرها باید با الگوی تأییدشدهٔ ارائه‌دهنده دقیقاً یکسان و از هم متفاوت باشند. برای SMS.ir شناسهٔ عددی قالب را وارد کنید. این الگو به‌هیچ‌وجه جایگزین الگوی OTP نمی‌شود.

نمونهٔ متن:

> {Name} عزیز، ورود به حساب شما در {Time} از IP {Ip} در {Source} انجام شد. اگر شما نبودید با پشتیبانی تماس بگیرید.

## رفتار و مرزها

- ورود موفق با رمز یا OTP در سایت و لانچر پوشش داده شده است. ورود خودکار پس از ثبت‌نام یا بازیابی رمز هم چون نشست تازه می‌سازد، مشمول تنظیم نقش است.
- ورود ناموفق، درخواست OTP، درخواست عادی با نشست یا توکن موجود و بازیابی نشست با کوکی remember اعلان جدید ندارند.
- اعلان به ایمیل و موبایل ثبت‌شدهٔ خود کاربر ارسال می‌شود. کانال بدون مقصد قابل استفاده رد می‌شود؛ کانال دیگر همچنان کار می‌کند. تأیید ایمیل شرط ارسال اعلان نیست.
- زمان، IP، User-Agent محدود به ۵۰۰ کاراکتر و محل ورود هنگام ورود ثبت و در payload صف نگه داشته می‌شوند. رمز، OTP، توکن و کلید دستگاه وارد پیام نمی‌شوند. محتوای متغیر در HTML escape می‌شود.
- IP از Request لاراول گرفته می‌شود؛ تنظیم trusted proxy پروژه باید با زیرساخت واقعی سرور تطبیق داشته باشد.
- سیاست نقش و مقصد هنگام ورود انتخاب می‌شوند؛ تغییر نقش یا اطلاعات تماس، اعلان‌های از قبل صف‌شده را بازنویسی نمی‌کند.
- هر کانال یک job مستقل دارد و فقط پس از commit تراکنش ارسال می‌شود. خطای dispatch گزارش می‌شود و ورود یا کانال دیگر را متوقف نمی‌کند. تراکنش rollbackشده پیام ارسال نمی‌کند.
- jobها حداکثر سه تلاش با فاصلهٔ ۱۵ و ۶۰ ثانیه بین تلاش‌ها دارند و timeout هر تلاش ۳۰ ثانیه است. مقدار سوم backoff برای سازگاری با افزایش تعداد تلاش‌ها ۱۸۰ ثانیه است. شکست نهایی در سازوکار استاندارد failed jobs/Horizon قابل مشاهده است.
- صف تحویل دقیقاً یک‌باره را تضمین نمی‌کند: اگر سرویس پیام را پذیرفته باشد ولی پاسخ آن قطع شود، تلاش مجدد ممکن است پیام تکراری بدهد. موفقیت transport نیز تضمین رسیدن به Inbox نیست.
- حافظهٔ داخلی تنظیمات پیش از هر job پاک می‌شود تا worker طولانی‌مدت، تغییر الگوی پیامک یا سرویس پیش‌فرض را از کش مشترک تازه بخواند.

برای مشاهدهٔ jobهای شکست‌خورده و تلاش مجدد پس از رفع تنظیمات:

```bash
php artisan queue:failed
php artisan queue:retry <job-id>
```

## استفاده از ایمیل در قابلیت‌های بعدی

از سرویس `App\Infrastructure\Services\Email\EmailService` و یک Mailable مخصوص همان قابلیت استفاده کنید:

```php
use App\Infrastructure\Services\Email\EmailService;
use App\Application\Identity\Mails\Auth\OtpMail;

app(EmailService::class)->queue($user->email, new OtpMail($code));
```

این نمونه فقط روش استفاده از سرویس را نشان می‌دهد و مسیر OTP فعلی برنامه همچنان پیامکی است. متد `queue` آدرس مقصد را اعتبارسنجی می‌کند، Mailable را clone می‌کند و job قابل تلاش مجدد را پس از commit در صف می‌گذارد. متد `send` برای ارسال فوری و تست دستی وجود دارد و همیشه هم‌زمان ارسال می‌کند؛ حتی اگر Mailable خودش `ShouldQueue` داشته باشد، دوباره به صف اضافه نمی‌شود.

قالب مشترک فارسی و راست‌به‌چپ `resources/views/emails/layout.blade.php` است. برای هر ایمیل جدید، قالب HTML و ترجیحاً نسخهٔ متن ساده تعریف کنید. از قرار دادن Request یا مدل‌های بزرگ و روابط بارگذاری‌شده در Mailable خودداری کنید؛ داده‌های لازم را در یک DTO کوچک به آن بدهید. اعتبارنامه‌ها و تنظیم transport در `.env` باقی می‌مانند و در پنل یا job ذخیره نمی‌شوند.

## بررسی پس از استقرار

روی نقش یک حساب آزمایشی، ایمیل را فعال کنید و یک بار خروج و ورود با رمز و یک بار ورود با OTP انجام دهید. هر بار باید یک اعلان در صف ثبت شود. سپس پیامک و الگوی تأییدشده را آزمایش کنید. در ورود لانچر، محل ورود باید «لانچر» باشد. ورود ناموفق و بازکردن صفحه با نشست موجود نباید اعلان تازه بسازند.

تست‌های خودکار هیچ ایمیل یا پیامک واقعی ارسال نمی‌کنند:

```bash
php artisan test tests/Feature/Identity/LoginAlertsTest.php tests/Unit/Identity/LoginAlertSmsPayloadFactoryTest.php
```
