# ایمیل فاکتور سفارش موفق

پس از رویداد `OrderPaidEvent`، برای سفارشی که صاحب حساب آن ایمیل معتبر دارد، یک فاکتور فارسی و راست‌به‌چپ ارسال می‌شود. این قابلیت خودکار فعال است و به گزینهٔ پیامک خرید یا اعلان ورود وابسته نیست. پرداخت درگاه، کیف پول، سفارش رایگان و تأیید پرداخت از مدیریت از رویداد مشترک سفارش استفاده می‌کنند.

فاکتور داخل بدنهٔ ایمیل شامل شماره سفارش، تاریخ شمسی پرداخت به وقت تهران، روش پرداخت و کد پیگیری موجود، تمام اقلام و افزونه‌ها، تعداد، قیمت واحد، تخفیف هر ردیف، تفکیک تخفیف محصولات و کوپن‌ها، مالیات و مبلغ پرداخت‌شده است. نسخهٔ متن ساده و لینک صفحهٔ سفارش‌ها نیز دارد. عنوان و مبلغ اقلام از snapshot خرید خوانده می‌شوند؛ تغییر یا حذف محصول در کاتالوگ روی فاکتور تأثیر ندارد. اطلاعات داخلی سفارش، یادداشت مدیریت و payload درگاه ارسال نمی‌شوند.

## استقرار

```bash
php artisan migrate --force
php artisan config:cache
php artisan horizon:terminate
# برای queue:work تحت process manager به جای Horizon:
# php artisan queue:restart
```

تنظیمات ایمیل فعلی برنامه در `.env` استفاده می‌شود. برای مثال، روی سروری که sendmail آن تنظیم شده است:

```dotenv
MAIL_MAILER=sendmail
MAIL_SENDMAIL_PATH="/usr/sbin/sendmail -bs -i"
MAIL_FROM_ADDRESS="your-real-sender@example.com"
MAIL_FROM_NAME="Cardiware"
MAIL_TIMEOUT=20
QUEUE_CONNECTION=redis
```

برای SMTP نیز transport و اعتبارنامه‌های فعلی `MAIL_*` کافی‌اند. مقدار `MAIL_MAILER=log` فقط پیام را در لاگ ثبت می‌کند و ایمیل واقعی نمی‌فرستد. مقدار `APP_URL` باید آدرس عمومی و صحیح سایت باشد تا لینک داخل ایمیل درست ساخته شود.

job از اتصال پیش‌فرض برنامه و صف پیش‌فرض همان اتصال استفاده می‌کند؛ بنابراین در محیط Redis، worker فعلی `supervisor-1` کافی است. در صورت نیاز، اتصال این قابلیت را مستقل تنظیم کنید:

```dotenv
ORDER_RECEIPT_QUEUE_CONNECTION=redis
```

اگر اتصال انتخاب‌شده از نوع `sync` یا `null` باشد، این job به اتصال `database` منتقل می‌شود تا پرداخت منتظر ارسال ایمیل نماند و پیام حذف نشود. در این حالت worker اتصال database نیز باید اجرا شود:

```bash
php artisan queue:work database --tries=3 --timeout=30
```

## رفتار صف و خطا

- ثبت در صف فقط پس از commit کامل تراکنش انجام می‌شود؛ rollback ایمیلی تولید نمی‌کند.
- `SendOrderReceiptJob` فقط شناسهٔ سفارش را در صف نگه می‌دارد. ایمیل فعلی خریدار، وجود حساب، وضعیت پرداخت‌شده و سابقهٔ ارسال هنگام اجرا دوباره بررسی می‌شوند. ایمیل خالی یا نامعتبر و سفارش لغوشده یا بازپرداخت‌شده ارسال نمی‌شوند. افزودن ایمیل پس از رویداد پرداخت، سفارش‌های قدیمی را خودکار بازسازی نمی‌کند.
- job یکتا و قفل `WithoutOverlapping` از ثبت و اجرای هم‌زمان تکراری جلوگیری می‌کنند. ستون‌های `receipt_email_sent_at` و `receipt_email_message_id` پس از پذیرش پیام توسط transport ذخیره می‌شوند؛ `updated_at` سفارش تغییر نمی‌کند. پذیرش پیام به معنی تضمین رسیدن آن به صندوق ورودی نیست.
- حداکثر سه تلاش با timeout سی‌ثانیه‌ای و فاصله‌های ۱۵ و ۶۰ ثانیه بین تلاش‌ها انجام می‌شود. خطای ارسال به مکانیزم retry صف می‌رسد و سفارش زودتر از ارسال موفق، ارسال‌شده علامت نمی‌خورد.
- اختلال در ثبت job، پرداخت قطعی‌شده را ناموفق نمی‌کند؛ خطا گزارش می‌شود. در صورت اختلال کامل صف، باید پس از رفع آن ثبت job برای سفارش‌های مربوط تکرار شود. این پیاده‌سازی outbox دائمی برای بازیابی خودکار اختلال ثبت در صف ندارد.
- اگر سرویس ایمیل پیام را بپذیرد ولی پاسخ قطع شود یا worker پیش از ذخیرهٔ نتیجه متوقف شود، تکرار ایمیل در retry ممکن است؛ SMTP تضمین ارسال دقیقاً یک‌باره ندارد.

شکست‌های نهایی در Horizon و failed jobs قابل پیگیری و retry هستند:

```bash
php artisan queue:failed
php artisan queue:retry <job-id>
```

تست‌ها از transport حافظه‌ای استفاده می‌کنند و ایمیل واقعی نمی‌فرستند:

```bash
php vendor/bin/phpunit tests/Feature/Commerce/OrderReceiptEmailTest.php
```
