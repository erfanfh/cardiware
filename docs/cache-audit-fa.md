# ممیزی کش صفحات سایت

تاریخ: ۲۰۲۶-۱۰-۱۹

این بررسی در سطح کد مسیرها، کنترلرها، اکشن‌های خواندن، کامپوننت‌های مشترک و مسیرهای نوشتن مرتبط انجام شده است. نتیجه، کش داده‌های قابل اشتراک است؛ پاسخ HTML کامل، نشست، CSRF، مجوز دانلود و وضعیت مالی کاربر وارد کش عمومی نمی‌شوند. اندازه‌گیری روی دیتابیس واقعی و Redis محیط production در این بررسی انجام نشده است.

## قواعد کش جدید

- پیاده‌سازی مشترک: `app/Application/Shared/Cache/PublicReadCache.php`.
- کلیدهای پارامتری با JSON و SHA-256 ساخته می‌شوند؛ نتایج خالی هم کش می‌شوند.
- TTL پیش‌فرض ۱۰ دقیقه است. داده‌های عمومی قرعه‌کشی، leaderboard، تعریف نظرسنجی و بلوک مشترک ویدئو TTL یک دقیقه دارند.
- کش‌های جدید وابسته به انتشار/زمان‌بندی، حداکثر تا نزدیک‌ترین تغییر `published_at`، `starts_at` یا `ends_at` معتبر هستند. متادیتای زمان بعدی نیز کش و با تغییر مدل باطل می‌شود.
- گروه وابستگی هر مدل با `CacheTag::publicModel()` مشخص می‌شود و رویدادهای save/delete/restore آن را باطل می‌کنند. restore از مسیر save مدل عبور می‌کند.
- تغییر روابط taxonomy در `SyncModelTaxonomyTermsAction` جداگانه ابطال می‌شود؛ ثبت رأی که شمارنده‌ها را با query builder تغییر می‌دهد نیز ابطال صریح دارد.
- داخل تراکنش ابطال فوری انجام می‌شود و پس از commit هم تکرار می‌شود تا cache refill هم‌زمان پیش از commit باقی نماند.
- آبجکت paginator پیش از تغییر مسیر و افزودن query string کپی می‌شود. اطلاعات درخواست و شخصی‌سازی کاربر در مقدار مشترک ذخیره نمی‌شوند.
- تغییرات رسانه، taxonomy، آیتم فروش و نویسنده علاوه بر کش جدید، tagهای مرتبط کش قدیمی را نیز باطل می‌کنند.

## اعتبارسنجی

تست‌های `tests/Feature/Cache/` خواندن بدون SQL تکراری در cache hit، انتشار بدون write جدید، تغییر زمان انتشار، جابه‌جایی دسته، sync روابط، تغییر/حذف رسانه، ویرایش/حذف/restore، عدم تداخل کلید SEO، جداسازی URL صفحه‌بندی، جداسازی preview، مخاطب پاپ‌آپ، انتخاب فرم استخدام، رأی کاربر و رتبه کاربر را پوشش می‌دهند. تست تراکنش نیز پرشدن مجدد کش پیش از commit را شبیه‌سازی می‌کند.

اجرای نهایی تست‌های مرتبط: **۱۲۴ تست موفق، ۷۱۷ assertion**. قالب‌بندی PHP با Pint و بررسی `git diff --check` نیز موفق بودند. سناریوی تخفیف کارت محصول، تازه‌شدن پس از ویرایش/حذف تخفیف و بازگشت کاربر restoreشده به leaderboard نیز بررسی شدند.

اجرای کامل مجموعه با `memory_limit=512M` روی ۸۱۱ تست انجام شد: ۴۳ error، ۱۰ failure و ۷ skipped داشت. هر ۵۳ مورد ناموفق با همان نام تست در یک کپی موقت از `HEAD` پیش از تغییرات کش نیز تکرار شدند؛ اختلافی بین فهرست تست‌های ناموفق دو نسخه وجود نداشت. این خطاهای قبلی شامل fixtureهای دانلود لانچر و ستون `downloads_count`، mock تنظیم `launcher_vpn_policy`، یک تست mock منو، فرم‌های حذف مدیریت، تست‌های ورود/امنیت، داده اولیه layout و تنظیم SMS بودند. این موارد خارج از اصلاحات کش حاضر باقی مانده‌اند. گزارش‌های محلی اجرای کامل و مقایسه baseline در `storage/logs/cache-audit-*.xml` نگهداری می‌شوند.

این صفر بودن SQL مربوط به اکشن‌های داده‌ای مشخص در تست است؛ تعداد کل query یک درخواست HTTP شامل احراز هویت، سشن، مجوزها و سایر کامپوننت‌ها جداست. تست‌ها از SQLite و cache store نوع array استفاده می‌کنند؛ سنجش latency، hit ratio و رفتار هم‌زمان Redis در production نیازمند اندازه‌گیری همان محیط است.

تغییر مستقیم جدول‌ها با SQL، `DB::table()` یا bulk update خارج از اکشن‌های بررسی‌شده رویداد مدل ایجاد نمی‌کند؛ چنین مسیر جدیدی باید `PublicReadCacheInvalidator::forModel()` را فراخوانی کند. فایل‌های cache store و تنظیمات محیط اجرایی در این تغییر دست‌کاری نشده‌اند.
