# کلید محتوا برای محصولات با دیتابیس رمزنگاری‌شده (Content Key Pipe)

این سند طرف Laravel قرارداد رو توضیح می‌ده. طرف لانچر (C#) و طرف Lua قراردادهای خودشون
رو توی `docs/CONTENT-KEY-PIPE-FA.md` مخزن MWLauncher دارن.

## چرا

برخی محصولات (مثل PGL6) فایل‌های دیتابیس بازی رو از قبل، آفلاین، با یه کلید ۳۲ بایتی
رمزنگاری می‌کنن. لانچر این کلید رو فقط برای کاربر مالک، فقط لحظه‌ی اجرا، از طریق یه
Named Pipe به پردازش بازی می‌ده — هیچ‌وقت به‌صورت فایل جدا روی دیسک کاربر نمی‌شینه.
سرور فقط باید این کلید رو، **فقط برای کاربرهای واقعاً مالک**، داخل همون مجوز آفلاین
امضاشده‌ی موجود (`/launcher/offline-license`) قرار بده.

## چیزی که اضافه شد

### ۱) دو ستون جدید روی `product_sale_item_manifests`

- `content_key_id` (رشته، حداکثر ۱۲۸ کاراکتر، **یکتا در کل جدول**): یه شناسه‌ی مبهم
  و نسخه‌دار — مثلاً `pgl6-db-2026-01`، **نه** اسم محصول. هر بار که دیتابیس دوباره
  رمزنگاری می‌شه (آپدیت فصلی)، این شناسه باید عوض بشه تا لانچر هرگز کلید قدیمی رو به
  دیتابیس جدید نده.
- `content_key_value` (متن، رمزشده در پایگاه‌داده با همون `'encrypted'` cast که
  `archive_password` هم داره): مقدار Base64 همون کلید ۳۲ بایتی (۲۵۶ بیتی) که دیتابیس
  باهاش رمزنگاری شده. **دقیقاً همون مقداری که توی اسکریپت رمزنگاری دیتابیس استفاده
  شده** — کاراکتر به کاراکتر.

هر دو از پنل ادمین، توی همون بخش «تنظیمات اجرا»ی هر نسخه فروش، زیر یه بخش جدید به اسم
«محافظت محتوا» قابل ثبت‌ان. دکمه‌ی «تولید تصادفی» یه کلید ۳۲ بایتی امن با
`window.crypto.getRandomValues` می‌سازه.

### ۲) اعتبارسنجی (`UpdateProductRequest`)

- هر دو فیلد یا با هم پر می‌شن، یا هر دو خالی می‌مونن (نه فقط یکی).
- `content_key_value` باید Base64 معتبر باشه که دقیقاً به ۳۲ بایت رمزگشایی بشه.
- `content_key_id` باید در کل جدول یکتا باشه (دو محصول مختلف نباید یه شناسه رو به
  اشتراک بذارن — چون هر دو داخل یه دیکشنری مشترک `content_keys` برای هر کاربر قرار
  می‌گیرن و تداخل می‌کنن).
- پشتیبانی از Sider باید برای این نسخه فروش فعال باشه (چون تحویل کلید فقط از طریق
  Pipe سمت Sider انجام می‌شه).

### ۳) `content_key_id` (نه مقدار کلید) داخل Manifest عمومی

`BuildPurchaseAccessManifestAction` فقط `content_key_id` رو داخل بخش `launch` قرار
می‌ده — **هرگز مقدار واقعی کلید رو.** این دقیقاً هم‌رده‌ی بقیه‌ی فیلدهای اجرا
(`main_executable_path`, `sider_executable_path`, ...) عمومیه، چون فقط یه شناسه‌ست،
نه یه راز.

### ۴) `content_keys` داخل payload امضاشده‌ی مجوز آفلاین

`IssueOfflineLicenseAction` حالا برای هر کاربر، فهرست محصولات قابل‌استفاده‌ش رو
می‌گرده (دقیقاً همون کوئری‌ای که برای `entitlements` هم استفاده می‌شه)، و برای
هرکدوم که `content_key_id`/`content_key_value` داشته باشه، یه ورودی به دیکشنری
`content_keys` اضافه می‌کنه:

```json
{
  "content_keys": {
    "pgl6-db-2026-01": "BASE64_KEY_EXACTLY_32_BYTES"
  }
}
```

این فیلد **داخل همون بخشی از payload قرار می‌گیره که با RS256 امضا می‌شه** (نه
Envelope بیرونی) — یعنی دستکاری‌اش بدون شکستن امضا ممکن نیست، دقیقاً مثل
`entitlements`. وقتی کاربر هیچ محصول محافظت‌شده‌ای نداره، این فیلد کلاً از payload
حذف می‌شه (نه یه دیکشنری خالی) — چون سمت لانچر (`System.Text.Json`) یه دیکشنری خالی
که از یه آرایه‌ی JSON خالی (`[]`) بیاد رو نمی‌تونه Deserialize کنه؛ حذف کامل فیلد
امن‌تره.

## صندوق رمزدار «محافظت محتوا» (جلوگیری از دسترسی ادمین‌های دیگر)

چون سایت ممکنه چند ادمین با دسترسی ویرایش محصول داشته باشه که نمی‌شه بهشون اعتماد
کامل کرد، فیلد `content_key_value` پشت یه **رمز کاملاً جدا از رمز ورود ادمین** قفله:

- رمز فقط به‌صورت Hash (نه متن ساده) در `CONTENT_KEY_VAULT_PASSWORD_HASH` (فایل
  `.env`) ذخیره می‌شه. با این دستور ساخته می‌شه:
  ```bash
  php artisan launcher:set-content-key-vault-password
  ```
- صفحه‌ی ویرایش محصول، **مقدار واقعی کلید رو هیچ‌وقت در HTML اولیه نمی‌فرسته** — فقط
  `content_key_id` (که راز نیست) و یه پرچم `content_key_configured` (بله/خیر) نشون
  داده می‌شه. مقدار واقعی فقط از طریق یه فراخوانی AJAX جدا
  (`POST admin/products/content-key/reveal`) و فقط بعد از وارد کردن رمز صندوق
  برگردونده می‌شه.
- این گیت فقط ظاهری نیست: حتی اگه یه ادمین با DevTools مرورگر، فیلد قفل‌شده رو
  دستکاری کنه و یه مقدار دلخواه بفرسته، **سمت سرور** (`UpdateProductRequest`) مقدار
  فعلی دیتابیس رو با مقدار ارسالی مقایسه می‌کنه؛ اگه واقعاً تغییر کرده باشه و رمز
  صندوق اخیراً (پیش‌فرض تا ۱۰ دقیقه، قابل تنظیم با `CONTENT_KEY_VAULT_UNLOCK_MINUTES`)
  وارد نشده باشه، ذخیره رد می‌شه.
- تلاش‌های ناموفق برای وارد کردن رمز صندوق Rate-Limit می‌شن (۵ تلاش هر ۵ دقیقه به
  ازای هر ادمین) و همه‌ی تلاش‌ها (موفق و ناموفق) در لاگ (`storage/logs`) با شناسه‌ی
  ادمین ثبت می‌شن.

## محصولات با چند نسخه‌فروش (مثلاً PGL6: نیم‌فصل / تمام‌فصل)

`content_key_id`/`content_key_value` روی هر **نسخه‌فروش** (`ProductSaleItem`) جدا
ثبت می‌شه، نه روی خودِ محصول. یعنی هر نسخه‌فروش کاملاً مستقله:

- **اگه دو نسخه فعلاً دیتابیس یکسانی دارن** (مثلاً چون هنوز به نقطه‌ی جدایی
  آپدیت‌هاشون نرسیدن): می‌تونید دقیقاً همون `content_key_id` و همون مقدار کلید رو
  برای هر دو ثبت کنید — عمداً این حالت مجاز گذاشته شده تا مجبور نباشید یه دیتابیس
  یکسان رو دوبار با دو کلید متفاوت رمزنگاری کنید.
- **قانونی که رعایت می‌شه:** یک `content_key_id` می‌تونه بین چند نسخه‌فروش مشترک
  باشه، **فقط اگه مقدار کلیدش هم دقیقاً یکی باشه.** اگه یه شناسه رو با یه مقدار
  کلید متفاوت دوباره ثبت کنید، رد می‌شه (برای جلوگیری از ابهام موقع ساخت
  `content_keys` سمت مجوز آفلاین).
- **وقتی مسیر آپدیتشون از هم جدا شد** (مثلاً نسخه‌ی تمام‌فصل یه آپدیت جدید می‌گیره
  ولی نیم‌فصل دیگه آپدیت نمی‌گیره): فقط نسخه‌ی تمام‌فصل رو با یه `content_key_id`
  **جدید** (طبق چک‌لیست پایین) به‌روزرسانی کنید؛ نسخه‌ی نیم‌فصل با همون شناسه و کلید
  قدیمی‌اش بدون هیچ تغییری به کارش ادامه می‌ده — چون این دو کاملاً مستقل از همن.

## چک‌لیست قبل از انتشار عمومی PGL6

0. یه‌بار (فقط خودت، نه برنامه‌نویس) اجرا کن: `php artisan launcher:set-content-key-vault-password`
   و خط خروجیش رو در `.env` بذار. این رمز رو جایی امن (نه چت، نه فایل مشترک) نگه دار.
1. یه `content_key_id` واقعی و یکتا (مثلاً `pgl6-db-2026-01`) و یه کلید ۳۲ بایتی
   *واقعی* (نه `MySecretTestKey123` تستی) توی پنل ادمین برای نسخه‌فروش PGL6 ثبت کنید.
2. دقیقاً همون مقدار Base64 رو در `encrypt_pesdb.py` (یا معادل نهایی‌شده‌اش) استفاده
   کنید تا فایل‌های واقعی دیتابیس رو رمزنگاری کنه.
3. مطمئن بشید پشتیبانی از Sider برای همین نسخه فروش فعاله (`capabilities.supports_sider`).
4. یه کاربر تستی واقعی رو با این محصول تست کنید: مجوز آفلاین بگیره، لانچر کلید رو
   داخل `content_keys` ببینه، Pipe کار کنه، بازی دیتابیس رو درست لود کنه.
5. برای هر آپدیت بعدی دیتابیس: `content_key_id` رو عوض کنید (نسخه‌ی جدید)، دیتابیس رو
   با کلید جدید (یا همون قبلی، دلخواهه) رمزنگاری کنید، و مقدار جدید رو در پنل ثبت
   کنید — هیچ تغییر کدی لازم نیست.
